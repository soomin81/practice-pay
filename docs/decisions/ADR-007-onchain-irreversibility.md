# ADR-007: 온체인 비가역성 — 금액이 맞지 않는 입금을 자동으로 되돌리지 않는다

- 상태: 승인

## 배경

카드 결제는 승인이 실패하면 고객의 돈이 빠져나가지 않는다. **온체인 전송은 그렇지 않다** —
고객이 USDC를 보낸 뒤에 검증이 실패해도 그 전송은 이미 확정돼 있고 되돌릴 수 없다. 즉
"결제 실패"와 "돈이 오지 않음"이 같은 뜻이 아니다.

`PaymentTransactionValidator`의 실패 사유를 **자금이 어디 있는지** 기준으로 나누면 셋이다.

| 구분 | 실패 사유 | 자금 위치 |
|---|---|---|
| 전송 자체가 실패 | `TRANSACTION_RECEIPT_FAILED` | 고객 지갑(빠져나가지 않음) |
| 우리 지갑 밖으로 감 | `RECEIVING_WALLET_MISMATCH`, `NETWORK_MISMATCH` | 제3의 주소(우리가 받지 않음) |
| **우리 지갑에 들어왔으나 결제로 인정되지 않음** | `AMOUNT_INSUFFICIENT`, `TOKEN_CONTRACT_NOT_ALLOWED` | **PG 수취 지갑** |

이 표의 "우리 지갑"은 **PG가 수탁하는 수취 지갑**을 뜻한다 — 수취 지갑이 가맹점 것이라면 자금
위치로 실패를 나누는 이 분류 자체가 성립하지 않는다(귀속 모델과 현재 API의 gap은
[MVP 범위](../architecture/mvp-scope.md)의 "수취 지갑 귀속" 절 참고).

세 번째가 문제다. 여기에 더해 **초과 지급**도 같은 성격이다 — 검증이 `받은 금액 >= 결제 금액`
이라 초과분이 있어도 결제는 성공하고, 정산은 견적 금액 기준으로 계산되므로 **초과분은 수취
지갑에 남는다**.

## 결정

**MVP는 이런 입금을 자동으로 반환하거나 정산에 반영하지 않는다.** 다음을 지킨다.

1. **결제 상태와 자금 보유를 분리해서 읽는다.** `Payment = FAILED`가 "받은 것이 없다"를 뜻하지
   않는다. 실제 수령 사실과 금액은 `blockchain_transaction`(`amount_minor`, `to_address`,
   `token_contract_address`)에 그대로 남는다 — 검증 실패로 결제를 실패시켜도 이 행은 지우지
   않는다.
2. **부족 지급은 결제를 성공시키지 않는다.** 부분 결제·추가 입금 대기·차액 청구는 MVP 범위
   밖이다(상태 머신에 부분 결제 상태를 두지 않는다).
3. **초과분과 부족분은 자동 환불하지 않는다.** 환불은 ADR-001에서 후속으로 미뤘고, 자동 반환
   경로를 만들면 반환 주소 검증·가스비 부담·재실패 처리라는 별도의 설계가 필요하다.
4. **위 두 경우는 운영 절차(수동)로 처리한다.** 온체인 기록과 `blockchain_transaction`을
   근거로 사람이 판단한다.

## 이유

- 자동 반환은 **새로운 실패 지점**을 만든다(반환 전송 실패·가스비·주소 오염). MVP가 감당할
  범위가 아니다.
- 그렇다고 "실패했으니 없던 일"로 두면 **PG가 고객 자금을 보유한 사실 자체가 기록되지 않는다.**
  결정하지 않은 것과 의식적으로 미룬 것을 구분하기 위해 이 ADR로 남긴다.
- 그래서 최소한의 방어선은 **수령 사실의 보존**이다(위 1번). 나중에 정산·환불을 구현할 때
  이 기록이 근거가 된다.

## 후속

- **금액 불일치를 1급 개념으로 승격**(예: `payment_discrepancy` — 결제와 실제 수령액의 차이를
  채권·채무로 기록). 지금은 `blockchain_transaction`을 사람이 조회해서 판단한다.
- 자동 환불(ADR-001의 환불 범위와 함께).
- **`CONFIRMED` 이후의 `REORGED`** — 확정된 입금이 체인 재구성으로 사라지는 경우. 되돌리려면
  `Payment = SUCCEEDED`와 그 뒤의 `ExchangeOrder`·`SettlementReceivable`까지 뒤집는 보상
  흐름이 필요해서 여전히 후속 범위다(필요 Confirm 수 12가 유일한 완화책이다).
  **확정 *이전*의 reorg는 이제 다룬다** — `DETECTED`/`CONFIRMING`에서 거래가 사라지면 유예 후
  `REORGED` + `Payment.FAILED(TRANSACTION_REORGED)`로 끝낸다(`state-transitions.md` 참고).
  이 경우는 아직 뒤따르는 개념이 없어서 이 ADR이 말하는 "확정 이후에 사실이 바뀌는 상황"에
  해당하지 않는다.
